# oh-my-taegun v1 Scope Freeze

## 목적

- 이 문서는 현재 제품 방향을 실행 가능한 명세로 고정하기 위한 v1 범위 합의 문서다.
- 상세 설계와 야간 실행 정책은 이 문서를 기준으로 `requirements.yaml`, `acceptance.yaml`, `spec.yaml`에 반영한다.

## 고정된 결정

### 1. 첫 사용자

- 1차 사용자는 제품 기획자 본인 1명이다.
- 다른 사용자는 제품의 직접 대상이 아니라, 각자 `git clone` 또는 skill 형태로 가져가서 재사용하는 확산 경로로 본다.

### 2. 저장소 입력 방식

- 사용자는 실행 전 질문 과정에서 다음 중 하나를 제공한다.
  - 대상 저장소의 `git URL`
  - 로컬 clone 디렉토리 경로
- 특정 언어, 프레임워크, 저장소 크기에 대해 제품 차원의 사전 제한을 두지 않는다.
- 대신 실행 전에 capability detection을 수행해 실제 지원 가능 범위를 판단한다.

### 3. 지원 범위 정책

- "지원 범위 무제한"은 구현 관점에서 다음 정책으로 해석한다.
  - 어떤 저장소든 입력은 받을 수 있다.
  - 실제 실행 가능 여부는 stack, build/test toolchain, 배포면, credentials, 외부 시스템 의존성을 탐지한 뒤 판정한다.
  - 지원 불가 또는 정보 부족 항목은 억지로 추론하지 않고 `blocked` 상태로 남긴다.

### 4. 낮 설계 완료 기준

- 낮 설계는 LLM이 스스로 판단하기에 야간 실행을 시작해도 더 이상 기획/설계를 구체화하지 않아도 되는 상태를 목표로 한다.
- 단, 다음 원칙을 반드시 지킨다.
  - 넘겨짚기 금지
  - 중요한 미확정 사항은 질문으로 해소
  - 질문 회피 금지
  - 실행 전제 조건이 불명확하면 `질문` 또는 `blocked`로 남김
- 운영적으로는 다음 조건이 모두 참일 때 설계 완료로 본다.
  - `open_questions = 0`
  - 모든 MUST 요구사항이 AC와 검증 방식에 연결됨
  - 저장소 입력과 브랜치 전략이 확인됨
  - 자격증명, 배포 대상, 외부 write 권한 필요 여부가 분류됨
  - 사용자 승인 기록이 남음

### 5. 밤 실행의 경계

- v1 야간 실행 범위에는 다음이 모두 포함된다.
  - 코드 수정
  - 의존성 설치
  - 테스트 실행
  - 배포
  - 외부 시스템 연동
- 다만 다음 고위험 작업은 정책 또는 명시적 승인 없이는 수행하지 않는다.
  - secret 사용
  - production deploy
  - database migration
  - 외부 시스템에 대한 write 작업
  - 인프라 변경

### 6. 아침 산출물

- 아침 산출물의 목표는 `real PR`이다.
- 기본 시나리오는 다음과 같다.
  - feature 브랜치에서 개발
  - 기능 검증 테스트 통과
  - regression test 통과
  - `develop` 브랜치 대상 PR 생성
- 원격 반영 실패, 권한 부족, 정책 불일치 시에는 코드를 폐기하지 않고 `blocked report`로 전환한다.

## 실행 프로파일

- 사용자 모드: `solo`
- 저장소 입력: `git_url | local_clone_path`
- 실행 모드: `sequential`
- 쓰기 작업공간: `isolated worktree`
- 딜리버리 목표: `real-pr`
- 딜리버리 실패 fallback: `blocked report`

## v1에서 반드시 지켜야 할 운영 원칙

- 시스템이 모르는 것을 아는 척하지 않는다.
- 질문해야 할 것은 반드시 질문한다.
- unsupported 영역은 실행하지 않고 근거와 함께 차단한다.
- 야간 실행은 장시간 무인 수행을 전제로 하지만, snapshot/handoff 없이 계속 진행하지 않는다.
- real PR은 테스트와 회귀 검증을 통과했을 때만 허용한다.

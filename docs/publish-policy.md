# Publish Policy

## 목적

- 이 문서는 oh-my-taegun을 로컬 중심으로 개발하다가, 나중에 GitHub 또는 skill 형태로 외부에 공개할 때 무엇을 올리고 무엇을 제외할지 정하는 기준 문서다.
- 기본 원칙은 `로컬에서 충분히 개발/테스트/실사용 -> 공개 가능한 부분만 선별 배포`다.

## 공개 전략

- 기본 개발은 로컬 git 저장소에서 진행한다.
- 공개 시점 전까지는 원격 저장소를 source of truth로 사용하지 않는다.
- 외부 공개는 다음 두 방식 중 하나로 진행한다.
  - 공개용 GitHub 저장소에 선별 push
  - skill wrapper 또는 설치 가이드 형태로 배포

## 공개 가능한 항목

- 제품 개요 및 설계 문서
- 공개 가능한 소스 코드
- 공개 가능한 테스트 코드
- 설치 방법, 실행 방법, 예제 설정
- 샘플 skill 템플릿 또는 wrapper 코드

## 기본 공개 제외 항목

- `.omt/` 이하의 모든 런타임 상태 파일
- snapshot, handoff, evidence registry, blocked report, local run state
- `.env`, secret, credential, certificate, key 파일
- 회사 내부 경로, 회사 전용 설정, 사내 도구 의존 설정
- 실사용 중 수집된 로그, 로컬 실험 흔적, 임시 스크립트
- 민감한 외부 시스템 endpoint 또는 운영 계정 정보

## 공개 전 점검 기준

### 1. 보안

- 토큰, 비밀번호, API key, 인증서가 저장소에 포함되지 않았는지 확인한다.
- 문서와 예제 코드에도 실계정 정보가 하드코딩되지 않았는지 확인한다.

### 2. 로컬 의존 제거

- 절대 경로, 회사 전용 툴 경로, 개인 장비 경로를 제거한다.
- 로컬 전용 실험 파일은 공개 브랜치에서 제외한다.

### 3. 문서화

- README에 목적, 설치 방법, 실행 흐름, 제약 사항을 정리한다.
- skill 형태 배포 시 필요한 입력과 제한 사항을 문서화한다.

### 4. 실행 가능성

- 공개 대상 코드가 최소한 설치와 기본 실행까지 재현 가능해야 한다.
- 공개 저장소에는 `example` 또는 `sample` 수준의 안전한 설정만 포함한다.

## 권장 공개 절차

1. 로컬에서 충분히 개발하고 실사용한다.
2. 공개 대상 파일만 포함하는 브랜치 또는 정리 커밋을 만든다.
3. 민감 파일과 런타임 산출물이 `.gitignore`에 포함되어 있는지 확인한다.
4. 공개 전 수동 리뷰를 수행한다.
5. 필요하면 공개용 README와 예제 설정을 추가한다.
6. 그 다음에만 GitHub 원격 저장소로 push한다.

## Skill 배포 정책

- skill 형태 배포 시에는 core 구현과 skill wrapper를 분리하는 것을 기본 원칙으로 둔다.
- skill에는 다음만 포함한다.
  - 사용 방법
  - 입력 형식
  - 호출 흐름
  - 공개 가능한 템플릿
- skill에는 런타임 상태 파일, 비밀값, 회사 전용 설정을 포함하지 않는다.

## 브랜치 전략 권장안

- 로컬 개발 기본 브랜치: `main`
- 공개 준비 브랜치: `publish/*`
- 공개 후 협업 브랜치 전략이 필요하면 별도 정의한다.
- 공개 전까지는 원격 `main`을 신뢰 원본으로 간주하지 않는다.

## 공개 보류 조건

- 민감 정보 제거 여부가 불확실할 때
- 회사 자산 또는 내부 설정 의존성이 남아 있을 때
- 재현 가능한 설치/실행 가이드가 없을 때
- 테스트 또는 최소 실행 검증이 끝나지 않았을 때
